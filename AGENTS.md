# AGENTS.md — working on Vera as an AI agent (Codex, Claude Code, others)

This file is for any AI coding agent working in this repository. Claude Code also loads the same procedures as
skills from `.claude/skills/`; everyone else should read the files listed below. **This is a public repository.**
Never put secrets, tokens, credentials, private data or personal content in code, commits, skills or board text.

## Golden rules

1. **Land through the Loop Lab pipeline onto `bleeding-edge`.** This applies to code, docs and skills alike, and
   never directly onto `main`. `main` and the production instance change only on the owner's explicit go-ahead.
   Never push to origin unless the owner asks.
2. **Commits are authored by the human.** No AI attribution anywhere: no co-author trailers, no "generated by" lines.
3. **Plans, handovers and evidence go ONLY in the shared planning area**,
   `<git-common-dir>/vera-work/shared-planning/<unit>/`. That is `/home/boejaker/Vera/.git/vera-work/shared-planning/`
   on the host, or `$(git rev-parse --git-common-dir)/vera-work/shared-planning/` from a worktree. It lives inside
   `.git`, so it is never committed or pushed. Read `shared-planning/README.md` first. Never write plans into
   `documentation/` (published product docs only), `Notes/`, the repo root, or your own home directory.
4. **Solid tasks live on the Loop Lab board** (`board.*` capabilities). Findings about someone else's area go as a
   comment on the related board item (search first). Claim before you edit.
5. **Status goes on the records your work already writes** (pipeline summaries and reviews, board progress
   comments), at each phase boundary and at least every ~25 minutes. Chat gets one line.
6. **Diagnose against the live instance, but never edit its checkout.** Prod's Redis traces, UI and behaviour are
   ground truth.
7. **Background model work follows the owner's rules:**
   - use the idle queue;
   - CPU-preferred (`prefer_gpu: false`), `job_type: idle_*`;
   - never put GPU work inside a running census;
   - yield via `census.control.set action=yield`.

## Reaching Vera's capabilities

- **MCP:** register the stdio bridge `vera/ide/vera_mcp_bridge.py` with `--caller-kind codex` (Claude uses
  `--caller-kind claude`), so your work is attributed to you. Don't reuse another agent's identity.
- **HTTP**, which works when the bridge doesn't or hides a capability:
  `POST https://<vera-host>:8999/mcp/call` with
  `{"name": "<cap.name>", "arguments": {...}, "caller_kind": "codex", "session_id": "<your session id>"}`.
  Check `GET https://<vera-host>:8999/health` before deciding Vera is down.
- Name yourself consistently: `codex:<session-id>` (board `frm`, worktree claim `owner`).

## Landing a change (short form; the full procedure is `improve-vera-sandboxed`)

1. `evolve.pipeline.begin(title, spawn=true, session_id)` creates the branch, worktree, container and pipeline. If
   the pool is full, use the hand-made worktree fallback in `improve-vera-sandboxed/LEARNINGS.md`.
2. Edit **only inside the worktree**. Claim a hand-made worktree at once (`evolve.worktree.claim`).
3. Commit **through the host** (`evolve.sandbox.exec where="worktree" …`). Git over the SMB share fails inside
   worktrees.
4. Test where imports resolve to your worktree (lowercase `vera.X` with the worktree on `sys.path`, or inside the
   branch's container). Run the critical tier via `evolve.unittest.run` / `evolve.pipeline.test`.
5. Review your own diff adversarially, record it (`evolve.pipeline.review`), then
   `evolve.pipeline.promote(id, to="bleeding-edge")` (`force=true` for docs/UI with no Python gate).
6. Update the board item and the unit's README. Write a handover if you stop mid-way.
